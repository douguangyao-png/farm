## 1. 调研

- **目标：** 做一套能给客户演示的四端前端：经营者后台、平台管理端、消费者小程序（H5）、管家 App（H5），用 mock 数据。演示完以后，换成真后端（芋道 master-jdk17）时页面代码不改。
- **影响面：** 都是新代码，不碰任何已有系统。会影响到的有两处：①这次定的 `/admin-api/farm/**`、`/app-api/farm/**` 接口路径和字段，后端开发要照着实现；②docs 里的命名（ER）要和 mock 数据统一。
- **同类：** 前端底座有三个，都是芋道官方仓库，2026-11-04 浅克隆调研：`yudao-ui-admin-vue3`（后台）、`yudao-mall-uniapp`（C 端）、`yudao-ui-admin-uniapp`（移动端后台，改成管家端）。三者的请求层都统一走 `{code, data, msg}` 包装，租户都放在请求头 `tenant-id`。
- **改法：** 单独写一个 Node mock 服务，按芋道的接口格式模拟后端，三个前端只把接口地址指向它。认养业务的页面加在各前端的新目录里；芋道自带的无关模块不改代码，只在菜单里不下发。

证据：
- [实测] `yudao-ui-admin-vue3` 最新提交 5dad4f4（2026-11-03），MIT 许可证。没有内置 mock，接口地址 `VITE_BASE_URL` + `VITE_API_URL=/admin-api`。菜单和权限在登录后由 `/system/auth/get-permission-info` 下发，租户开关是 `VITE_APP_TENANT_ENABLE`，请求头 `tenant-id`。
- [实测] `yudao-mall-uniapp` 最新提交 9b3af41（2026-11-01），MIT 许可证，JS 写的（不是 TS）。接口 `SHOPRO_API_PATH=/app-api`，租户 `SHOPRO_TENANT_ID`。现有页面有：商品、订单、支付、用户、优惠券、分销、聊天。
- [实测] `yudao-ui-admin-uniapp` 最新提交 bc0bf01（2026-11-02），基于 unibest 4.1.0（Vue3 + TS + uni-app）。已有 iot、mall、bpm 等分包，租户开关和后台一样。
- [文档] 12 号文档：C 端 47 页、后台 34 页、管家 17 页，平台端没有原型。这次只做演示主线用到的页面，见 R-1。

## 2. 需求

术语：
- **mock 服务：** 用 Node 写的假后端，按芋道接口格式返回数据，数据放在内存里，启动时从种子文件加载，可以一键重置。
- **演示主线：** 给客户讲的一条跨四个端的完整故事，见 3.1。
- **mock 模式 / 真后端模式：** 构建时用环境变量切换。两种模式下页面代码完全相同，区别只在接口地址。

不做：
- 不做后端（Java）。分账、真实支付、真实电子合同、真实 IoT 接入、真实直播都不做，在页面上用「演示数据」代替，并且标出来。
- 不做繁育档案、繁育链路（用户 2026-11-04 定）。
- 不做 12 号文档里的全部页面，只做演示主线和 R-1 列出的页面。
- 不改芋道的系统管理页面（用户、角色、菜单、字典等），原样保留，菜单里能看到就行。
- 不发布微信小程序。C 端和管家端演示时用 H5（浏览器的手机模式或手机扫码）。
- 不做营销（券、拼团、分销）、社区、会员积分、AI 问诊。

- R-1 当演示人按 3.1 的主线操作时，四个端应能连贯走完，并且一端的操作在另一端能看到结果。主线覆盖的页面：

## 3. 设计

### 3.0 方案对比

| 方案 | 做法 | 复杂度 | 风险 | 对现有代码的影响 | 以后好不好改 |
|---|---|---|---|---|---|
| A | 每个前端在请求层里各自拦截返回假数据 | 低 | 四端数据不互通，C 端下单后台看不到，主线讲不通；mock 代码进了前端包，切真后端要删 | 改三个前端的请求层 | 差：mock 逻辑分散在三处 |
| B | 单独写一个 Node mock 服务，按芋道接口格式实现，三个前端只改接口地址 | 中 | 要多跑一个服务；mock 接口和以后的真接口可能对不上 | 前端请求层不用动 | 好：mock 接口就是后端契约草稿，换后端只改地址 |
| C | 现在就把芋道后端跑起来，直接开发后端 | 高 | 违背「先演示再做后端」的顺序，周期长 | 无 | 好，但慢 |

选择：B。原因：只有 B 能让四端共用一份数据，主线讲得通；mock 服务里的接口定义可以直接当后端契约。代价是多维护一个服务，以及契约要提前定（见 3.3）。

### 3.1 交互（演示主线）

1. 平台管理员登录后台 → 开通租户「青山农场」，选专业版套餐。
2. 经营者登录 → 建基地 → 建地块 A-01（挂摄像头和传感器）→ 发布认养商品「一分菜地 · 年度认养」，配置三档托管。先输入违禁词演示被拦截（R-2），再改成正确文案后提交。
3. C 端用户打开 H5 → 首页 → 商品详情选半托管 → 确认订单 → 勾选合同（R-3）→ 模拟支付 → 我的认养。**后台订单列表出现这一单。**
4. 经营者在订单详情里看到认养关系和地块 A-01。
5. 管家登录管家端 → 今日任务 → 农事打卡（上传照片，GPS 和环境数据自动带入）→ 提交。**后台审核通过后，C 端生长档案多一条。**
6. C 端认养详情：生长档案、溯源六段、环境数据曲线、监控画面（视频占位）。
7. C 端自管任务有一条已逾期 → 委托代办（R-5）→ **管家端出现代管工单** → 接单、打卡完成。
8. C 端农资商城买一袋有机肥（必须绑定地块）→ 后台农资订单。
9. 后台录入收成 → 配送批次 → C 端收获配送里看到物流信息。
10. 经营者工作台和风险自检；平台端风控预警。

### 3.2 技术

- **仓库结构**（farmer-saas 初始化为 git 仓库）：
  ```
  farmer-saas/
    docs/              现有文档
    web-admin/         来自 yudao-ui-admin-vue3（经营者后台和平台端共用，按账号区分）
    app-member/        来自 yudao-mall-uniapp（C 端 H5）
    app-steward/       来自 yudao-ui-admin-uniapp（管家端 H5）
    mock-server/       Node + TS，实现 /admin-api 和 /app-api
  ```
  三个前端各自固定在调研时的上游提交（5dad4f4、9b3af41、bc0bf01），作为第一次提交导入，之后改动都是增量，方便以后对比和合并上游。
- **新增业务代码放哪**：后台放 `web-admin/src/views/farm/`、`src/api/farm/`；C 端放 `app-member/pages/farm/`、`sheep/api/farm/`；管家端放 `app-steward/src/pages-farm/`。芋道已有文件只改三处：环境变量、主题色和产品名、菜单或首页入口。
- **mock 服务**：Node 20+ 和 TS。数据在内存里，启动时从 `mock-server/seed/*.json` 加载，`POST /__mock/reset` 重置。系统类接口（登录、权限菜单、字典、租户）照芋道的返回格式实现；业务接口按 3.3 的契约实现。按请求头 `tenant-id` 和 token 做租户隔离（R-6）。
- **切换模式**：每个前端新增 `.env.mock`，接口地址指向 mock 服务，`VITE_MOCK_BADGE=true`；真后端用芋道原有的 `.env.prod`。演示角标只在 mock 环境变量为真时渲染（R-7）。
- **命名**：以 12 号文档 9.2 节的实体为准并统一：`steward`（不用 keeper）、`asset_id`（不用 land_id）、`member`（不用 customer）。托管模式字段 `care_mode` 放进 order 和 adoption。统一后的结果写进契约，再回改 02 号文档（另起任务，不在本方案内）。

- DDL：不涉及。demo 阶段没有数据库；字段定义写在契约里，后端开工时再出 DDL，另写方案。

# 11 · 后端技术选型评估：.NET 是否可行？

> 评估对象：认养农业 SaaS（B2B2C 多租户经营中台）
> 评估目的：**以"最快交付"为第一目标**，判断 .NET 作为后端技术栈是否成立
> 版本核对日期：2026-10-25 ｜ 结论：**可行，且在"新组建小团队 + 复杂业务 + 快速交付"场景下是优选**

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 用户量撑得住吗？ | **完全撑得住，且余量巨大**。本项目 Y3 峰值预估 QPS 800（大促 3000），ASP.NET Core 单实例即可覆盖，性能从来不是这个业务的瓶颈 |
| 交付速度真的快吗？ | **快，但快的来源不是"C# 语法"，而是轮子齐全**：ABP（多租户/权限/审计开箱）、EF Core（建模+迁移）、SignalR（实时推送）、Hangfire（任务引擎）、CAP（可靠事件）—— 这 5 个轮子直接省掉 6–8 周自研基建 |
| 有没有坑？ | 有 3 个真实风险：**招聘池小于 Java**、**部分国内农业/政务 SDK 只有 Java 版**、**ABP 学习曲线** —— 都有明确应对方案，见第四节 |
| 什么时候不该选 .NET？ | **你手上已经有一支能打仗的 Java 团队时，不要换栈。** 换栈风险 > 收益，用 Spring Boot + MyBatis-Plus 交付速度差距不到 10% |
| 最终建议 | 新组建团队、你本人能定架构 → **.NET 10 LTS + ABP Framework（或精简自建）+ EF Core + PostgreSQL**；这是本方案后续所有文档的默认技术栈 |

**一句话判断**：这个产品的瓶颈是**业务复杂度**（认养/托管三档/农资/责任矩阵/分账/溯源/合规），不是**并发量**。技术栈选择的正确权重是：开发效率 50%、可维护性 25%、生态适配 15%、招聘 10%。.NET 在前两项上是满分。

## 二、先算清楚：这个产品的真实体量（选型的唯一依据）

### 2.1 用户量与并发模型（3 年目标）

| 指标 | Y1（试点） | Y2 | Y3（目标） | 测算依据 |
|---|---|---|---|---|
| 租户（B 端经营者） | 30–50 | 150 | **500** | 全国 1.8 万+ 共享农场项目，按 3% 转化 |
| 单租户认养人数 | 均值 200 | 均值 300 | **均值 350** | 小微 80–300 / 中型 300–800 / 区域龙头 1000+ |
| C 端注册用户 | 1 万 | 4.5 万 | **17.5 万** | 租户数 × 均值 |
| MAU | 3,000 | 1.4 万 | **5.2 万** | 认养人月活约 30%（收菜/看记录/收通知） |
| DAU | 500 | 2,400 | **8,800** | MAU × 17%（非高频社交型产品） |
| 日均请求量 | 6 千 | 3 万 | **10.5 万** | DAU × 12 次请求 |
| **峰值 QPS** | 10 | 80 | **常规 60–120；推送瞬间 400–800；大促 ≤3,000** | 管家发一条农事记录 → 数千人同时点开，是本系统最典型的尖峰形态 |
| B 端后台账号 | 200 | 750 | 2,500 | 500 租户 × 5 子账号 |
| B 端 QPS | <5 | <10 | **<20** | 后台操作低频 |

### 2.2 数据规模

| 对象 | Y3 规模 | 存储方案 |
|---|---|---|
| `order` 订单 | 30 万行 | PostgreSQL |
| `growth_record` 生长档案（最大业务表） | 500 万行 | PostgreSQL（按租户+时间分区） |
| `input_record` 投入品台账 | 300 万行 | PostgreSQL |
| `sensor_data` 传感器时序 | 4–8 亿点 | **TimescaleDB（PG 扩展）或 TDengine**，热数据 30 天 |
| 业务库总体积 | **< 120 GB** | 单主一从即可，无需分库分表 |
| 图片/视频 | 3–8 TB | 对象存储（OSS/COS/MinIO）+ CDN |

### 2.3 由此得出的三条硬结论

1. **不需要微服务**。500 租户、QPS 800 的量级上微服务只会拖慢交付。用**模块化单体（Modular Monolith）**，按业务域分项目，未来按需拆出。
2. **不需要分库分表**。120GB 业务库，PostgreSQL 单实例绰绰有余；索引 + 缓存足够。
3. **性能不是约束条件**。真正消耗工期的是：多租户隔离、权限、审计、任务引擎、分账、支付回调幂等、溯源存证 —— 这些正是成熟框架能替你解决的。

> **⚠️ 选型时最容易犯的错**：拿"未来可能有百万用户"当理由去上微服务/K8s/分库分表。按 2.1 的表，Y3 峰值 800 QPS，这套系统用两台 4C8G 就能扛。**把省下来的 6–10 周全部投到业务功能上，这才是"快速交付"的正解。**

## 三、.NET 可行性论证

### 3.1 版本事实（已核对官方支持策略，2026-10-25）

| 版本 | 发布 | 类型 | 终止支持 | 建议 |
|---|---|---|---|---|
| **.NET 10** | 2025-11-11 | **LTS** | 2028-11-14（Active 阶段） | ✅ **新项目唯一选择** |
| .NET 9 | 2024-11-12 | STS | 2026-11-10 | ❌ 即将 EOL |
| .NET 8 | 2023-11-14 | LTS | **2026-11-10** | ❌ **半个月后终止支持**，新项目不要踩 |

> 这条很关键：如果团队惯性说"用 .NET 8 稳"，要注意它在本月中旬就 EOL 了。**新项目直接上 .NET 10 LTS。**

### 3.2 .NET 与本项目的 8 个匹配点

| # | 本项目难点 | .NET 的对应能力 | 提速效果 |
|---|---|---|---|
| 1 | **多租户隔离**（所有表 tenant_id，禁止越权） | ABP Framework 内置 `IMultiTenant`、租户解析器、`ICurrentTenant`、自动数据过滤；也支持按租户独立库 | 省 **1.5–2 周** |
| 2 | **复杂业务模型**（16+ 表、认养关系、责任矩阵、分账规则） | EF Core Code First + Migration + LINQ；强类型重构安全；JSONB 字段映射 | 建模与演进省 **2 周** |
| 3 | **任务引擎**（作物日历 / IoT 阈值触发、逾期 48h 自动转委托工单） | **Hangfire** 或 Quartz.NET：持久化调度、失败重试、可视化 Dashboard | 省 **2 周** |
| 4 | **实时能力**（IoT 推送、管家聊天、农事记录通知） | **SignalR** 原生支持 WebSocket/SSE/长轮询自动降级，带 Group 与重连 | 省 **1.5 周** |
| 5 | **可靠事件**（支付成功 → 生成认养 → 分账 → 上链 → 推送） | **dotnetcore/CAP**：本地消息表 + Outbox 模式，支持 RabbitMQ/Kafka/Pulsar，最终一致 | 省 **1.5 周** |
| 6 | **IoT 接入**（EMQX MQTT 订阅、传感器入库） | **MQTTnet** + `BackgroundService`（`IHostedService`）常驻托管服务 | 省 **1 周** |
| 7 | **权限与审计**（平台/经营者/管家/财务四级角色 + 操作留痕） | ABP 内置 权限/角色/审计日志/工作单元（UoW）/领域事件 | 省 **1.5 周** |
| 8 | **合规校验**（商品文案禁"保底/稳赚"、农药禁零售） | FluentValidation + MediatR Pipeline Behavior，集中式规则管道 | 省 **0.5 周** |

**合计约省 11–14 周基建工期** —— 这就是"快速交付"的真实来源。

## 四、风险与应对（说真话的部分）

| # | 风险 | 严重度 | 应对方案 |
|---|---|---|---|
| R1 | **招聘池小于 Java**：想从 6 人扩到 20 人时，.NET 中高级供给偏紧 | 中 | ① MVP 期只需 2 名后端，规模内完全够招；② 用"1 资深 + 1 中级"结构，资深定架构与领域模型；③ 后期若扩招困难，业务代码是标准分层，转 Java 重写单模块可控 |
| R2 | **部分第三方 SDK 无 .NET 版**（尤其地方政务、农业物联网硬件、部分电子合同厂商） | 中 | ① 优先选有 OpenAPI/HTTP 接口的服务商（e签宝/法大大/快递鸟/微信支付均有 REST API）；② 用 Flurl.Http 封装，单个对接 1–2 天；③ **选型前对 6 家关键供应商做一轮 SDK 确认**（见附录 C 清单），这是唯一必须前置核实的事 |
| R3 | **ABP 学习曲线陡**（DDD/聚合根/模块化概念重，不熟会拖慢 2–3 周） | 中高 | **采用"轻量 ABP"用法**：只用其多租户、权限、审计、工作单元、Blob；**不强行全套 DDD**。若团队无 ABP 经验，走**路线 B 自建精简版**（多租户+权限+审计约 1.5 周自研，完全可控）——见第七节决策树 |
| R4 | **信创/私有化要求**（麒麟 OS + 达梦/人大金仓） | 低-中 | ① .NET 10 跨平台，麒麟可跑；② **国产数据库 EF Core Provider 成熟度不如 Java 侧 MyBatis 生态**，若客户强制，必须提前做 1 周 POC；③ 在合同里明确"数据库以 PostgreSQL/MySQL 为准，国产库另行评估报价" |
| R5 | **被 Blazor 诱惑**：想用 C# 一把梭写后台 UI | 低 | ❌ 不建议。后台 UI 组件生态与前端招聘都不如 Vue3。**后台坚持 Vue3 + Element Plus，前后端分离** |
| R6 | **.NET 在国内 SaaS 圈"存在感低"**，投资人/合作方有偏见 | 低 | 用交付速度说话：12 周 MVP 落地试点；性能数据（单机吞吐）反而更好看 |

## 六、容量与成本测算（给老板看的数字）

**资源规划**

| 阶段 | 应用实例 | 数据库 | 缓存 | 月成本（估） |
|---|---|---|---|---|
| Y1 试点（≤50 租户） | 1 × 2C4G | PG 2C4G 100G（主）+ 备 | Redis 2G | **≈ ¥800–1,200** |
| Y2（150 租户） | 2 × 4C8G | PG 4C8G 200G 主从 | Redis 4G | **≈ ¥1,800** |
| Y3（500 租户，峰值 800 QPS） | **3 × 4C8G**（N+1 冗余） | PG 4C8G 300G 主从 | Redis 8G + 对象存储/CDN | **≈ ¥2,300–3,000** |

**性能余量**：按 ASP.NET Core 带 EF Core 查询 + Redis 缓存的典型接口保守 **500 RPS/实例（4C8G）** 估算，Y3 峰值 800 QPS 时 2 实例即可，部署 3 实例留 50% 余量。**大促 3000 QPS 场景**：读接口走 Redis + 静态化，写接口限流排队，临时扩容到 6 实例即可覆盖。

> 对比：同规模 Java(Spring Boot) 方案通常需要 1.5–2 倍内存规格，三年云成本多支出约 **¥1.5–3 万**——不是决定性因素，但方向有利。

## 七、决策树：选 .NET 还是别的？

```
你手上有现成的、能打仗的后端团队吗？
├─ 有，且是 Java → 用 Java 17/21 + Spring Boot + MyBatis-Plus + ruoyi/若依 类脚手架
│                   （不要换栈：换栈风险 > 收益，交付差距 < 10%）
├─ 有，且是 .NET → 直接按本方案执行 ✅
└─ 没有 / 新组建 → 选 .NET 10
                    ├─ 团队有人熟悉 ABP/DDD → 路线 A：ABP Framework（省 3–4 周）
                    └─ 全队都不熟 DDD      → 路线 B：ASP.NET Core 精简自建
                                              （多租户/权限/审计自研约 1.5 周，
                                                代码完全可控，无学习税）
```

**路线 A vs B 对比**

| | 路线 A：ABP Framework | 路线 B：精简自建 |
|---|---|---|
| 起步成本 | 学习 1–2 周 | 自研基建 1.5 周 |
| 得到什么 | 多租户、权限、审计、设置、Blob、后台作业、本地事件总线 | 只做多租户 + JWT 权限 + 审计（够用即可） |
| 风险 | 团队不熟 DDD 会写出四不像 | 长期需自己维护基建 |
| **建议** | 团队 ≥1 人有 ABP 经验时选 | **默认推荐（对最快交付最稳）** |

## 八、选型决策的时间盒

> **别在选型上花超过 1 周。** 技术栈对交付速度的影响（±10%），远小于"需求边界是否收敛"和"是否复用成熟框架"（±40%）。
>
> 唯一必须前置核实的事：**附录 C 里 6 家第三方供应商的 .NET SDK / OpenAPI 可用性**（微信支付、电子合同、物流、短信、对象存储、IoT 平台）。这轮核实 2 天就能做完，做完就可以开工。
